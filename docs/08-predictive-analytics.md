# 08. Предиктивная аналитика и визуализация инсайтов

**Версия:** 1.0 · **Дата:** 2026-10-03 · Зависимости: [doc 02](02-modules.md) §5–6, [doc 03](03-data-model.md), [doc 07](07-nli-rubert-reuse.md)

Отвечает на три вопроса: (1) какие ML-модели работают в предиктивном контуре и где именно; (2) как аналитика и статистика отображаются в UI, чтобы давать реально полезные инсайты; (3) как работает вкладка «Аналитика компании», собираемая по графу совпадающих телефонных номеров.

---

## 1. Реестр ML-моделей предиктивного контура

Единый реестр (дублируется в `models_registry` БД). Каденс: `call` — на каждый звонок в пайплайне; `day` — ночная витрина; `week` — еженедельная задача; `live` — на запрос.

| # | Модель | Задача и выход | Вход (фичи) | Каденс | Холодный старт | Качество/приемка |
|---|---|---|---|---|---|---|
| M1 | **objection-clf** — RuModernBERT-base, multi-label | классы возражений + спан (цитата) → `objections` | окно реплик ± контекст | call | лейблы: weak supervision + разметка ([doc 06](06-datasets.md)) | F1 ≥ 0.75 per class |
| M2 | **response-nli** — rubert multitask_v2 (ADR-14) | отработка возражения (`handled_*`), критические ошибки → `violations`, evidence скоринга | пара «реплика клиента → ответ агента» | call | чистый корпус тренажёра + InfoBayAI-пары | NLI-Acc ≥ 0.93, F1-Contr ≥ 0.92 |
| M3 | **embed** — USER2-base | векторы фраз/звонков/компаний → `embeddings` | тексты, профили | call / day | готовая модель, бенчмарк retrieval | Recall@5 ≥ 0.85 |
| M4 | **risk-deal** — CatBoost + SHAP | вероятность потери сделки за 14/30 дней → `risk_assessments` (call/deal level) | эмбеддинг звонка (M3), структурные метрики, события (M1/M2), граф-фичи (цепочка: глубина, тишина в днях, доля неотвеченных), CRM-фичи | call + nightly переоценка активных сделок | глобальная модель + **abstention до N≥100 исходов org** | AUC ≥ 0.70, побитие baseline-логрегрессии |
| M5 | **risk-account** — CatBoost / скоринговая карта (см. ниже) | **агрегированный риск по компании**: отток/срыв в 30 дней → `insights` + карточка компании | взвешенный пул звонковых рисков M4 по компании, тренды возражений/тональности, recency (дней с последнего контакта по графу), доля звонков без ЛПР, число неотвеченных входящих, изменение talk_ratio | nightly | **детерминированная скоринговая карта** (правила из метрик, без ML) до N≥30 компаний с исходами | AUC ≥ 0.65 + калибровка; карта до этого |
| M6 | **trend-anomaly** — STL/EWMA + PSI (лёгкий, без нейросетей) | аномалии метрик команды/компании/агента: падение скоров, рост пауз, всплеск возражений типа X → `insights` | временные ряды витрин (§2) | day | работает сразу (статистика) | precision@k на ручной валидации ≥ 0.6 |
| M7 | **sentiment-emo** — голова на RuModernBERT, инициализация Dusha | тональность реплик + траектория звонка | реплики | call | Dusha-лейблы, дообучение на своих | F1 ≥ 0.70 |
| M8 | **domain-clf** — голова классификации отрасли | отрасль компании → обогащение фильтров и фич M4/M5 | транскрипты компании | day | MaratDV-метки доменов | F1 ≥ 0.8 |
| M9 | **similar-success** (v2) — kNN по эмбеддингам M3 | «похожие ситуации, чем закончилось»: для звонка/компании → топ-5 похожих с исходами | вектор текущего контекста | live | работает сразу после M3 | ручная оценка полезности |
| M10 | **next-best-action** (v2, опционально) — на кластерах M9 + правилах | рекомендация следующего шага → `insights` | контекст компании + статистика успешных путей | nightly | правила из рубрик | A/B на пилотах |

**Принципы реестра:** каждая модель пишет результат в свою таблицу с `model_id+version` и объяснением (SHAP/цитаты); всё, что можно посчитать правилами без ML, считается правилами (M6 — статистика, M5 cold start — карта); ни одна модель не попадает в UI без eval-приемки ([doc 02](02-modules.md) §9) и режима abstention.

**risk-account — как считается (M5, ядро вкладки компании):**

```text
features_company = {
  risk_deal_pooled:  Σ(w_i · risk_i) / Σw_i,   w_i = длительность·recency звонка i,
  risk_trend:        наклон risk по последним 5 звонкам,
  silence_days:      дней с последнего исходящего контакта (по графу всех телефонов),
  unanswered_ratio:  доля пропущенных входящих за период,
  obj_price_unhandled_ratio, obj_trend_top: топ-возражение и его динамика,
  no_dm_ratio:       доля звонков без ЛПР (роли из M2/NER),
  sentiment_slope:   наклон траектории тональности,
  chain_depth, deals_open, crm_stage_stall_days
}
cold start: scorecard = Σ(weights · bucketed(features)) → 0..100, веса из литературы+эксперта;
  после N≥30 компаний с исходами → CatBoost, SHAP-факторы обязательны.
```

## 3. Вкладка «Аналитика компании» — по графу телефонов (главная фича)

### 3.1 Можно ли? Да — и данные уже есть

Граф ([doc 03](03-data-model.md) §4) связывает `phone_number ↔ contact ↔ company` и хранит **все** телефоны компании (включая исторические). Все транскрипты, скоры, возражения и риски уже лежат по звонкам — вкладка компании это **агрегация по union звонков всех телефонов компании за период** + ML-выводы M4/M5 + инсайт-лента.

### 3.2 Резолюция «звонок → компания» (алгоритм)

```text
1. Явные CRM-связи (bitrix24/amoCRM: deal_id/contact_id) — приоритет 1, confidence=1.0
2. phone_norm → entity_links(has_phone, phone_match) → contacts → company
   (по всем историческим номерам; связь имеет valid_from/valid_to — номер,
   «переехавший» к другой компании, не тянет старые звонки за пределы периода владения)
3. NER-упоминания названия компании в транскриптах (Yargy) → кандидаты, confidence<1
4. Ручное слияние/перепривязка в UI (создаёт/правит entity_links, source=manual, аудит)
Итог: звонок участвует в аналитике компании, если путь (1)–(2) с valid-окном;
(3) — только в подсказках для ручного подтверждения, не автоматически.
```

Граничные случаи, заложенные в дизайн: **общий/корпоративный номер** у нескольких компаний (связи конкурируют — побеждает CRM-связь, остальные требуют manual-подтверждения); **смена владельца номера** (valid_to обрезает историю); **холдинги** (несколько юрлиц — ручная группировка компаний в группу, агрегация по группе опциональна).

### 3.3 Что показывает вкладка (макет)


API: `GET /api/v1/companies/{id}/analytics?period=90d` — риск+факторы, лента инсайтов, тренды, цепочка звонков со ссылками на транскрипты, участники/ЛПР, похожие компании. Guardrails: звонков < 3 → показывается скоринговая карта с бейджем «мало данных», ML-числа скрыты; все цитаты проходят PII-политики роли ([doc 04](04-security-152fz.md)).

### 3.4 Почему это «реально полезный инсайт», а не дашборд-витрина

Каждый элемент вкладки отвечает на вопрос «что делать»: риск-карточка даёт факторы (куда давить), лента — конкретные события с цитатами и таймкодами, похожие компании — референсы успешных путей. Сравнение per-criterion с тренажёром (ADR-15) добавляет действие: «слабость X → назначь сценарий Y в тренажёре».

## 4. Остальные экраны аналитики

### 4.1 Дашборд РОПа

- **Риск-борд**: топ-10 компаний/сделок по M5/M4 с факторами; сортировка «деньги × риск»; клик → вкладка компании;
- **Командные тренды**: скорость/возражения/критерии таксономии по команде vs прошлый период; аномалии M6 с ack;
- **Лидерборд по критериям таксономии** (не по менеджерам-«лучшему/худшему», а по критериям: где команда системно проседает → назначить тренажёр);
- **Воронка стадий** диалогов (M-стадии из [doc 02](02-modules.md) §3.2): где звонки «умирают».

### 4.2 Инсайт-лента (кросс-экранная)

Единый формат события: `что случилось (метрика-дельта) → доказательство (звонки/цитаты) → что делать (гипотеза действия)`. Правила анти-шума: severity-иерархия (риск денег > аномалия > тренд > стат), дедупликация похожих событий, ack/dismiss с запоминанием, дайджест-режим (daily/weekly digest вместо realtime-спама). Всё, что нельзя подкрепить доказательством, — не инсайт, а метрика.

### 4.3 Экран менеджера и аналитика

- **Менеджер**: свои звонки, персональный вектор слабостей по таксономии, прогресс после тренировок в тренажёре (per-criterion, ADR-15);
- **Аналитик**: когорты (отрасль M8 × исход), срезы по возражениям/стадиям, semantic-поиск «покажи звонки, где говорили о X» (pgvector), экспорт обменного формата ([doc 05](05-exchange-format.md));
- **DPO**: комплаенс-дашборд (согласия, ретенции, аудиты — [doc 04](04-security-152fz.md)).

## 5. Технические заметки

- Все витрины считают только обработанные звонки (`state=done`) — частично обработанные не попадают в тренды (защита от «пилы»);
- Кэш дашбордов — Redis, инвалидация по завершении nightly-джобов;
- Вычисление M5/M6 nightly: бюджет < 5 мин на 1000 активных компаний (CatBoost CPU + SQL-агрегаты);
- `insights` хранит доказательства как ссылки (call_id, quote_ref) — не копии текста (PII-политики применяются на чтении);
- Экспорт аналитики компании в обменный формат (layer B) — кнопка «Создать сценарий из слабости» в UI (замыкает ADR-15 в продуктовом UX).
