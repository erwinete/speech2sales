# 06. Датасеты и стратегия данных

**Версия:** 1.0 · **Дата:** 2026-10-03 · Проверено через HF API и карточки датасетов

Стратегия использования открытых корпусов для: бенчмарка ASR на телефонном канале 8 кГц, дообучения энкодера на реальных диалогах «агент–клиент», эмбеддингов и ML-моделей (риск, возражения), отработки диаризации и разметки ролей.

| Объём | заявлено автором ~1025 ч (двухканальная) — **проверить по карточке после принятия гейта** |

**Чек-лист верификации после принятия гейта** — **выполнен 2026-10-03** (токен пользователя, datasets-server + tree API):

1. **Транскриптов в датасете НЕТ** — единственная колонка `audio` (список ссылок на WAV). Эталон WER — только ручная разметка (§6), NLI-пары — через псевдоразметку своим ASR ([doc 07](07-nli-rubert-reuse.md) §5, сценарий B).
2. Аудио: **8 кГц моно** (single) — телефония; заявленная обработка включала PII-muting и шумодав.
3. Разметка сверх аудио отсутствует (только аудио-колонка).
4. **На HF размещены только сэмплы, а не 1025 часов**: single-channel = 3 звонка (~30 мин, `Russian/Sample-01..03.wav`), dual-channel = 3 звонка в формате **двух моно-файлов на звонок** (`SPEAKER_00.wav` + `SPEAKER_01.wav` — раздельные каналы агента/клиента). Полный корпус — коммерческая поставка (связь с вендором). Следствие: **основной bulk-источник для бенчмарков — MaratDV (832 ч, §1.2)**, InfoBayAI — сэмплы для smoke/диаризации (S1–S3).
5. Репрезентативность: на сэмплах — реальная телефония, средняя длительность ~10 мин.

**Двойная роль датасета (решено 2026-10-03):** (1) эталон распознавания — ручная разметка сэмплов (3 звонка) → бенчмарк WER (§6); (2) источник «звонков» для dev-стенда ([doc 09](09-dev-stand.md)) — пилотный заказчик на старте разработки не требуется. Инструменты: `tools/datasets/fetch_infobayai.py`, `fetch_dual.py` (сборка стерео из SPEAKER-пар), `inventory.py`, `benchmark_asr.py` (S5).

## 2. Главный вывод по рынку датасетов

**Открытого русского аудио-датасета именно по продажам (возражения, исходы сделок, роли) не существует** (проверено: HF search, Kaggle, коммерческие маркеты). Ближайшее: InfoBayAI — свежий и лицензионно чистый (CC BY 4.0), но это колл-центр вообще (поддержка+продажи, состав уточняется); MaratDV — прода́жные домены внутри, но без транскриптов и с лицензией «без перераспространения».

→ **Гибридная стратегия** (§3): InfoBayAI как база для ASR-бенчмарка и диаризации, Dusha — эмоциональная голова, saas-sales-russian — прототип риск-модели и сценариев тренажёра, MaratDV — стресс-тест доменного покрытия (авто/банки/недвижимость), а **разметку возражений и прода́жных сигналов делаем сами** — это и есть moat продукта (плюс лейблы от пилотных заказчиков).

## 3. Матрица использования «задача → датасет → работа»

| Задача | Датасет | Что делаем | Трудозатраты |
|---|---|---|---|
| **Бенчмарк ASR на 8 кГц** (GigaAM-v3 vs T-one vs Whisper) | InfoBayAI dual+single, MaratDV | Golden-набор: стратифицированная выборка ~10 ч (по доменам/шуму), ручная транскрипция эталона. Замер WER/RTF/VRAM: T-one (нативные 8 кГц), GigaAM-v3 (апсемпл 8→16 кГц: soxr-VHQ vs линейный; и вариант «T-one как препроцессор»), Whisper-v3-turbo. Гипотеза: T-one выиграет на грязной 8 кГц, GigaAM — на чистой | разметка 10 ч ≈ 30–40 ч работы; бенчмарк-скрипт — 2–3 дня |
| **Роли и диаризация** | InfoBayAI dual | Каналы = ground truth ролей. Протокол: (1) оценка точности нашей эвристики карты каналов; (2) downmix в моно → pyannote 3.1 / Sortformer → сравнение DER и назначения ролей с канальной истиной; (3) отбор порогов для «когда доверять каналам» | скрипты + отчёт — 3–5 дней |
| **Дообучение энкодера (DAPT + контрастив)** | InfoBayAI (транскрипты, если есть) + MaratDV (псевдо-транскрипты своим ASR, conf > порога) + внутренние пилотные транскрипты | Этап 1 — DAPT: MLM-продолжение RuModernBERT-base на телефонных транскриптах (сленг, озвучка цифр, обрывы фраз). Этап 2 — контрастив дообучение (SimCSE-стиль, пары «реплика-позитив из того же звонка/соседние реплики») для эмбеддингов. Оценка: ruMTEB-подвыборка + наш retrieval-набор (Recall@5 ≥ 0.85) | GPU-ночи; код 4–6 дней |
| **Головы классификации (возражения/сигналы)** | InfoBayAI/MaratDV (кандидаты) + **своя разметка** | Лейблов возражений нет нигде → weak supervision (правила-лексиконы дают черновые метки) + ручная разметка ~1 500 возражений и ~800 сигналов (активное обучение). Плюс перенос эмоций из Dusha для тональности | разметка ≈ 40–60 ч; окупается v1.0 |
| **NLI-пары для скоринговой головы** (ADR-14, [doc 07](07-nli-rubert-reuse.md)) | InfoBayAI dual-channel (транскрипты или псевдо-ASR) + чистый корпус тренажёра (15 994 + 2 999 пар) | двухканальность = автоматическая генерация пар «реплика клиента → ответ агента» без ручной диаризации; авто-разметка правилами + LLM-аннотатором, выверка 1–2k руками | сборка пар — 2–3 дня после транскриптов |
| **Эмбеддинги и риск-модель** | saas-sales-russian (прототип), затем InfoBayAI + исходы пилотов | Прототип пайплайна риск-модели на текстах с outcome/engagement (проверка фич, CatBoost, SHAP, time-split) — до появления реальных исходов. Прод-модель — только на данных пилотных заказчиков (см. abstention в [doc 02](02-modules.md) §6) | прототип 3–5 дней |
| **Доменный классификатор (о какой отрасли звонок)** | MaratDV (метки доменов из коробки!) | Голова классификации отрасли — полезно для маршрутизации рубрик и аналитики | 1–2 дня |
| **Тренажёр: сценарии из реальных звонков** | InfoBayAI (после ручного отбора) | Отбор звонков с яркими возражениями → обезличивание → сборка TrainerScenario по [doc 05](05-exchange-format.md) (CC BY 4.0 позволяет с атрибуцией) | непрерывно |

## 4. Конвейер подготовки (`polylog.datasets`, скрипты в `tools/datasets/`)

```
HF (token, gated accept) → скачивание → MinIO datasets/{dataset}/{version}/
→ инвентаризация (md5, длительность, SR, каналы) → нормализация (как в прод-пайплайне)
→ сплиты: benchmark_asr / diarization_eval / dapt_train / labeling_pool
→ манифесты (jsonl) с источником, лицензией, атрибуцией
```

Правила:

1. **Один и тот же код нормализации** для датасетов и прод-аудио — иначе бенчмарки ASR не переносимы на прод.
2. Сплиты фиксируются манифестами с hash — воспроизводимость eval (практика из [doc 02](02-modules.md) §9).
3. Датасет-репо не коммитим в продукт-репо; данные живут локально/в приватном MinIO. Для MaratDV — дополнительно запрет на публичный хостинг производных (условие лицензии).
4. Проверка PII в транскриптах публичных датасетов перед дообучением на них голов (Natasha-скан; находки — маскируем).

## 5. Юридические заметки

- **CC BY 4.0** (InfoBayAI): совместим с AGPL-ядром (данные ≠ код); атрибуция — в карточке модели и в `NOTICE.md` продукта («fine-tuned on Russian Call Center Audio Dataset by InfoBayAI, CC BY 4.0»).
- **MaratDV**: коммерческая лицензия без перераспространения — можно обучать и бенчмаркать, нельзя публиковать датасет/производные аудио; веса моделей, обученные на нём, публиковать осторожно (указать происхождение; юридическая консультация перед публичным релизом таких весов).
- **Dusha/Sber**: лицензия — PDF в репозитории golos; если окажется research-only — используем только для внутренних экспериментов и замены на свои лейблы в проде.
- **152-ФЗ не применяется** к публичным обезличенным датасетам напрямую, но наш продукт, дообученный на них, обязан сохранять свои гарантии (§PII [doc 04](04-security-152fz.md)).
- **Решение 2026-10-03 (ADR-17):** юридические проверки отложены. Локальная разработка, dev-стенд и пилоты не блокируются; публичный релиз на GitHub и публикация весов/производных корпусов — только после юр. ОК (см. оговорки в [doc 07](07-nli-rubert-reuse.md) §6).
