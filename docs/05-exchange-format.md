# 05. Обменный формат «Call Artifact / Trainer Scenario»

**Версия спецификации:** 1.0.0-draft · **Дата:** 2026-10-03 · Схемы: [schemas/](../schemas/)

Это **точка интеграции** между локальной платформой аналитики и SaaS-тренажёром возражений (и любыми другими потребителями). Принципы:

1. **Нулевая связность** — обмен только файлами (JSON/YAML) или HTTP-выгрузкой; никаких прямых доступов к БД и API платформы.
2. **Два слоя** — слой A «артефакты звонка» (факты из аналитики) и слой B «сценарии для тренажёра» (учебные конструкции, собранные из артефактов). Слой B может собираться как платформой, так и вручную/LLM-ассистентом в тренажёре — формат один.
3. **Претендент на отраслевой стандарт** — спека и схемы живут в отдельном репозитории под CC0; семантическое версионирование; minor-версии только additive; каждый документ несёт `schema_version`.
4. **Приватность по умолчанию** — поля ПДн маскируются согласно политике org ещё на стадии экспорта; экспорт логируется.

---

## 1. Слой A — «артефакт звонка» (`call_artifact`)

### Правила слоя A

- Все находки (`objections`, `signals`) обязаны иметь `quote` и `start_ms` — объяснимость переносится в формат.
- `previous_call_id`/`chain_depth` — для восстановления контекста цепочки потребителем.
- `provenance` обязателен: потребитель должен знать, чем и как получены факты.
- ПДн: `participants.display_name` уже отфильтрован политикой; поле `pii_policy` декларирует, что применено.

## 2. Слой B — «сценарий для тренажёра» (`trainer_scenario`)

Собирается из одного или нескольких артефактов (`source_call_ids`). YAML — основной вид (редактируется методологом тренажёра):

```yaml
schema_version: "1.0.0"
scenario_id: "scn-existing-supplier-b2b-saas"
spec: "trainer-scenario/1.0"
title: "Возражение «у нас уже есть поставщик» — B2B SaaS"
persona:
  role: "руководитель отдела закупок среднего бизнеса"
  company_profile: "оптовая торговля, 80 сотрудников"
  temperament: "скептичный, занятой, ценит конкретику"
  crm_context: "второй звонок, на первом отказался от демо"
opening_line:
  text: "Здравствуйте, у нас уже есть поставщик, повторять не нужно."
  variant_of: "obj-1"          # связь с артефактом-источником
objections:
  - id: "obj-1"
    trigger_phrases:
      - "мы уже работаем с поставщиком"
      - "у нас договор с другой компанией"
    client_quote_ref: {"artifact_id": "01J9F2XQ7M5T8ZC3V6B0N4R8W2", "objection_id": "obj-1"}
    ideal_responses:
      - text: "Предлагаю не менять, а сравнить: если мы не лучше — честно скажу."
        why: "не отрицает лояльность, переводит в критерии сравнения"
      - text: "А что сейчас важнее всего — цена или стабильность поставок?"
        why: "открывает критерии решения"
    bad_responses:
      - text: "А вы не пробовали нас?"
        why: "игнорирует контекст, звучит навязчиво"
    difficulty: 2
success_criteria:
  - id: "crit-1"
    description: "Менеджер не спорит с лояльностью к поставщику"
    weight: 3
    detection: {"kind": "semantic", "hint": "признание текущего поставщика"}
  - id: "crit-2"
    description: "Задан ≥ 1 вопрос о критериях выбора"
    weight: 4
    detection: {"kind": "semantic", "hint": "вопросы про цену/сроки/условия"}
  - id: "crit-3"
    description: "Получено согласие на следующий шаг"
    weight: 3
    detection: {"kind": "semantic", "hint": "договорённость о звонке/встрече"}
metadata:
  source_call_ids: ["01J9F2XQ7M5T8ZC3V6B0N4R8W2", "01J8Z0K3P9Q2R5T8V1X4C7B0M3"]
  industry: "b2b_saas"
  language: "ru"
  license: "CC-BY-4.0"           # лицензия самого сценария
  anonymization: "mask"          # уровень обезличивания источников
```

### Правила слоя B

- Каждый элемент трассируется к источнику (`client_quote_ref`) или помечается как сконструированный.
- `detection` — декларативный; исполняется движком тренажёра (LLM-судья), формат лишь описывает критерии.
- Сценарий самодостаточен: не ссылается на данные платформы, только на артефакты внутри пакета.

## 3. Пакет и доставка

- Минимальная единица — файл; пакет — `.zip` с `manifest.json` (список артефактов/сценариев, версия спеки, чек-суммы).
- Доставка: ручной экспорт из UI, `GET /api/v1/exports/{job}` (подписанный URL, TTL), исходящий webhook с файлом (SFTP/S3/HTTP push) — настраивается.
- Обратной связи из тренажёра в v1 нет (тренажёр сам решает, что делает с результатами тренировок); в v2 — опциональный `scenario_feedback` слой по той же спеке.

## 4. Версионирование и эволюция

| Изменение | Версия | Правило |
|---|---|---|
| Новые опциональные поля/enum-значения | minor (1.1) | additive-only; старые потребители обязаны игнорировать неизвестные поля |
| Удаление/переименование, смена семантики | major (2.0) | период сосуществования ≥ 2 minor-версий; генератор пишет обе версии |
| Исправление схем без влияния на данные | patch (1.0.1) | схемы публикуются с `$id` и точной версией |

Канонические enum'ы (v1): `objection.type` — 10 классов таксономии платформы + `other`; `response.status` — 5 статусов; `signal.kind` — 6 видов; `risk.abstained` требует `abstain_reason`. Полные списки — в схемах.

## 5. Качество формата (как обеспечиваем)

- JSON Schema (draft 2020-12) — источник истины; CI-тесты: все фикстуры проходят валидацию; roundtrip JSON↔YAML без потерь.
- Golden-примеры: 10 артефактов из анонимизированных реальных звонков + 5 сценариев — в репозитории спеки.
- Conformance-набор для сторонних генераторов/потребителей: `polylog spec validate <file>`.

## 6. Дорожная карта v1.1 — общий семантический слой с SaaS-тренажёром (утверждено, ADR-15)

Прямая интеграция с тренажёром отсутствует по дизайну (§0), но выгрузка должна **обогащать** тренажёр: данные должны быть понятны ему без реинтерпретации. Механизм — общий семантический слой из двух компонентов.

### 6.1 Общая таксономия `taxonomy.json` (ядро)

Третий артефакт CC0-репозитория спеки, рядом с двумя JSON-схемами:

- **Единое ID-пространство**: `obj.*` (возражения), `sig.*` (сигналы), `resp.*` (статусы отработки), `crit.*` (критерии/ошибки), `skill.*` (навыки) — с v1.1 источник истины для enum'ов обеих схем;
- Оба продукта зависят от **версии таксономии**, а не друг от друга; релизный цикл независимый;
- Governance — как у формата: additive-only в minor, `other` как catch-all, депрекация через major. Аналитика тянет длинный хвост классов для детекции, тренажёр получает стабильный обучаемый набор — разъезд «совпадающих голов» невозможен по построению.

### 6.2 Общая голова классификатора (сильная форма)

- «Полилог» обучает multitask_v2 (ADR-14: NLI-голова + мультилейбл-голова таксономии) и публикует **чекпойнт + thresholds.json как релизный артефакт** (офлайн-бандл/HF); лицензия весов объявляется явно — Apache-2.0 или CC-BY-4.0 (AGPL-код обучения автоматически на веса не переносится, фиксируем лицензию явно);
- Тренажёр подключает чекпойнт **нулевым количеством кода** — `rubert_backend` уже загружает формат multitask_v2 (`RUBERT_MODEL_DIR` на папку весов);
- Одинаковая голова + одинаковые пороги = совпадение вердиктов на одинаковых парах «реплика клиента → ответ агента» в обоих продуктах.

### 6.3 Additive-поля формата (v1.1)

| Поле | Где | Смысл |
|---|---|---|
| `taxonomy_version` | корень артефакта и сценария | версия таксономии, на которую ссылаются все ID |
| `success_criteria[].detection.criterion_id` | слой B | якорь критерия в таксономии (сейчас `detection` декларативен) |
| `metadata.rubric_ref`, `metadata.weakness_ref` | слой B | из какой рубрики/пункта аналитики порождён сценарий — трассировка цикла |
| `ideal_responses[].evidence` | слой B | `{source_call_ids, win_rate_delta}` — ответы, заминенные из реальных звонков с дельтой исхода |

Слой A в v1.1 не меняется: `model_id` у находок уже есть, веса в формат не переносятся.

### 6.4 Замкнутый цикл обогащения

Аналитика на реальных звонках находит слабое место (`crit.objection_handling` на `obj.price`, доля `handled_success` 0.3) → выгрузка несёт находки с теми же ID → тренажёр порождает сценарий, где success_criteria ссылаются на тот же критерий → отработка → readiness по критерию сравним с показателем команды. Потоки: реальные цитаты → `trigger_phrases`; удачные ответы из реальных звонков → банк `ideal_responses`; кластеры новых возражений (objection_pattern, [doc 02](02-modules.md) §5) → новые шаблоны сценариев.

### 6.5 Что сознательно НЕ синхронизируем

- **Экземпляры рубрик**: рубрика аналитики — org-специфичный конфиг, критерии тренажёра — продуктовые; общее только ID-пространство;
- **Калибровка и пороги**: распределения «реальный клиент» и «симуляция-персона» различны — сравнимы per-criterion исходы и тренды, не абсолютные скоры; каждый продукт калибруется на своём, формат несёт сырые находки с `model_id`;
- **Live-скоринг через формат**: формат — пакетная выгрузка, не канал realtime-обмена.
