# 02. Дизайн модулей

**Версия:** 1.0 · **Дата:** 2026-10-03

Детальные контракты модулей «Полилога». Каждый модуль — Python-пакет с чистым интерфейсом; плагины регистрируются через entry-points.

---

## 1. Модуль ингеста и коннекторы (`polylog.ingest`)

### 1.1 Contract SDK

```python
class TelephonyConnector(Protocol):
    id: str                      # "freepbx", "bitrix24", "amocrm", "s3watch", ...
    def verify(self, cfg: ConnectorConfig) -> HealthReport: ...
    def discover(self, since: datetime, cursor: Cursor) -> list[CallRef]: ...
    def download(self, ref: CallRef) -> AudioFile: ...
    def metadata(self, ref: CallRef) -> CallMeta:
        """direction, участники, номера, карта каналов (agent/client),
        consent_flag, crm_refs (deal_id, contact_id), started_at, duration"""
```

- `discover()` — поллинг по расписанию ИЛИ приём webhook (`POST /api/v1/hooks/{connector}`) с HMAC-проверкой; оба пути создают одну и ту же запись `calls` (идемпотентность по `external_id`).
- Conformance-тесты: фикстуры записанных ответов АТС; каждый коннектор обязан их проходить (контрактный тест по аналогии с provider-контрактами).

### 1.2 Матрица коннекторов

| Коннектор | Способ обнаружения | Получение аудио | Карта каналов | Consent-флаг | CRM-связи | Статус |
|---|---|---|---|---|---|---|
| FreePBX/Asterisk | CDR (postgres/ODBC) или AMI events | HTTP/SFTP из `/var/spool/asterisk/monitor` | из имени файла (`q-4586-…-in.wav`) или CDR | из IVR-конфига (запись объявлена) | через CRM-коннектор по номеру+времени | ✅ код+тесты |
| **Cisco UCM/CUBE** | flat CDR-файлы на SFTP (`cdr_flat_*.csv`) | Unified Recording/MediaSense по URL из CDR | поле CALLING/OBCALLED + конфиг линии | из UCL-лицензии | через CRM-коннектор | ✅ парсер+тесты; SFTP — M2 |
| **Oktell** | MS SQL база (`Calls`: CallID/CallStart/PhoneIn/PhoneOut/TalkLen) | UNC `\\server\Records\` или HTTP по CallID | по LineType/направлению | из настроек записи Октелла | частично | ✅ парсер+тесты; SQL — M2 |
| **MightyCall** | REST API `/calls` (поллинг) | recordingUrl с bearer-токеном | по направлению | recordingConsent | нет | ✅ клиент+тесты (MockTransport) |
| Битрикс24 | webhook `onVoximplantCallEnd` (+ поллинг REST) | tokenized URL записи | по направлению | да | нативно: call → lead/deal/contact | ✅ парсер+webhook-эндпоинт; REST-enrich — M2 |
| amoCRM | REST `/api/v4/calls` (OAuth) | CDN-ссылка с токеном | по in/out | да | lead/contact в payload | ✅ клиент+тесты; OAuth-токены — M2 |
| S3/watch | список бакета по префиксу | прямое скачивание | по соглашению об именовании | нет → политика org | нет | план |
| Generic HTTP | `POST /api/v1/calls` с файлом | прямая загрузка | поля формы | поле формы | optional refs | ✅ работает |

**Webhook-приём (реализовано):** `POST /api/v1/hooks/{connector}` — HMAC-SHA256 тела
(секрет `POLYLOG_HOOK_SECRET_{KIND}`), дедуп по external_id, пайплайн запускается
только при наличии записи (звонки без аудио ждут скачивания). Статусы: 202 принят,
`created: false` — дубликат.

**Правило связки с CRM:** звонок первично связывается с контактом через `phone_norm` (E.164) + окно времени ±48ч; если CRM прислала явные refs — они приоритетнее. Все связи пишутся в граф-таблицу `entity_links` с `source` (crm|phone_match|ner_match|manual) и `confidence` — см. [doc 03](03-data-model.md) §4.

## 2. Медиа-обработка и ASR (`polylog.media`, `polylog.asr`)

### 2.1 Нормализация (`media`)

- Вход: любой контейнер/кодек (wav/alaw/mp3/m4a/ogg).
- Выход: PCM WAV 16 бит. Каналы: если 2 канала и карта известна → сохраняем стерео (ch0=agent, ch1=client по метаданным коннектора, верифицируется энергией+эвристикой приветствия); иначе → моно 16 кГц.
- T-one принимает телефонные 8 кГц нативно; GigaAM — 16 кГц. Храним нормализованную копию 16 кГц (апсемпл при необходимости), оригинал не трогаем.
- Метаданные стадии: sha256, длительность, RMS-профиль (для пауз), SNR-оценка (для отчёта «качество записи»).

### 2.2 VAD

**Silero VAD** (MIT, ONNX, CPU, RTF ≈ 0.01) — мировые паузы, сегментация для ASR, статистика пауз для метрик. Пороги и min-silence — конфигурируемы per-org.

### 2.3 Роли (speakers)

1. **Каналы**: карта из коннектора. Валидация: если >90% первых 3 секунд тишины на «агентском» канале — переворачиваем карту и помечаем `role_map_status=auto_flipped`.
2. **pyannote 3.1** (моно/конференции): диаризация → кластеры → назначение ролей эвристикой (первый активный = агент; распределение времени; скрипт приветствия). Для >2 спикеров роли: `agent_1/agent_2/client_*`.
3. Ручная правка в UI → событие в `labels` (см. §10).

### 2.4 ASR-адаптеры

```python
class AsrBackend(Protocol):
    id: str                                   # "gigaam-v3-rnnt", "t-one", "whisper-v3-turbo", "vosk"
    def transcribe(self, wav: Audio, roles: RoleMap, hints: TranscribeHints) -> list[Utterance]:
        """Utterance: speaker_role, start/end (ms), text, words[] (word, start, end, conf),
        avg_conf, language, backend_id, backend_version"""
```

- Выбор бэкенда: политика org (`primary`, `fallback_chain`), автоматический фолбэк при ошибке/WER-деградации/отсутствии GPU.
- Батчинг: чанки ≤ 60с по VAD-границам, батч 8; длинные монологи шьются на фразы по паузам.
- Выходная артефакт: `transcript.json` в MinIO + строки `call_segments` в БД (текст, тайминги, conf, роль).

### 2.5 Пунктуация и денормализация

- **Пунктуация/капитализация:** `ai-forever/sbert_puncase_ru` (CPU, лёгкая) для GigaAM/T-one сырого вывода; Whisper пунктуацию несёт сам.
- **Денормализация чисел:** конвертация словесных чисел → цифры («восемь девятьсот шестьдесят…» → телефон) — критично для извлечения ПДн, сумм и дат; собственный нормализатор на pymorphy2 + правила.

### 2.6 Доменный словарь организации (три слоя)

| Слой | Что делает | Где живёт |
|---|---|---|
| L1. Пост-ASR коррекция | фонетические гомофоны → канонические термины: русский фонетический ключ + RapidFuzz (порог ≥ 0.85), учёт слитного/раздельного написания брендов | таблица `lexicon_entries` (term, aliases, phonetic_key, category, case_sensitive) |
| L2. Словарь в UI | РОП загружает список: названия продуктов/компаний, жаргон, аббревиатуры; импорт CSV; слова влияют на L1 и на NER-факты | `lexicon_entries` + версия словаря, hash |
| L3. ASR-байес (research) | CTC shallow fusion / WFST-лексикон / Whisper initial_prompt | флаговые фичи, не в MVP |

Каждая правка L1 помечается `correction_source=lexicon` и хранит `raw_text` — аудит и пере-применение при изменении словаря (репроцессинг только сегментов с высоким фаззи-скором).

## 3. NLP-анализ (`polylog.nlp`)

### 3.1 Сегментация анализа

Анализ оперирует **репликами** (utterances) и **окнами** (реплика ± 1 соседняя с той же стороны диалога). Длинные реплики режутся на предложения (Natasha segmentation).

### 3.2 Головы на RuModernBERT-base (дообучение — §8)

| Задача | Тип | Классы (стартовая таксономия) | Выход |
|---|---|---|---|
| Детекция возражений | multi-label sentence classification ( utterance + context window) | цена; «уже есть поставщик»; «пришлите КП»; сроки; не тот, кто решает; доверие к компании; «не интересно»; юридические/договорные; сравнение с конкурентом; другое | {type, prob, span_text, start/end, speaker} |
| Отработка возражения | pair classification: (возражение, следующая реплика агента) | handled_success / handled_partial / ignored / deferred («вышлю КП и вернусь») / failed | {status, response_span, response_latency_ms} |
| Сигналы интереса | multi-label | согласие на след. шаг; упоминание бюджета; сроки закупки; подтверждение ЛПР; запрос деталей/документов; позитивная реакция на демо | {kind, span, prob} |
| Тональность | 3-class per utterance (agregate → траектория) | positive/neutral/negative | {label, prob, trajectory} |
| Стадии диалога | sequence classification по репликам + Viterbi-сглаживание | greeting → identification → qualification → presentation → objection_handling → negotiation → closing → goodbye | {stage, span} |
| Факты (NER) | Natasha NER + Yargy-грамматики: имена, организации, суммы, даты, телефоны, email | — | facts[] (для Customer 360 и ПДн-конвейера) |
| Запрещённые фразы | правила + лексикон (орудия скрипта: оскорбления, обещания вне скрипта, слова-паразиты — конфигурируемо) | — | violations[] |

### 3.3 Метрики разговора (без ML, из таймингов VAD/слов)

- **talk_ratio** по ролям (agent/client, % речи от speech-time)
- **паузы**: count/total/longest (межрепликовые гэпы > 2с), **interruptions** (перекрытия на стерео)
- **вопросы**: количество вопросов агента/клиента (punctuation + wh-лексикон), вопросы/мин
- **темп речи** (слов/мин), **монологи** (longest agent/client turn)
- **тишина** (доля VAD-тишины), **односторонние паузы** (кто молчал)

### 3.4 Вычислительный контракт

Все находки обязаны иметь: `span_text` (цитата), `start_ms/end_ms`, `prob`, `model_id+version`, `features_hash`. UI никогда не показывает классификацию без цитаты.

## 4. Скоринг (`polylog.scoring`)

### 4.1 Рубрики

Рубрика = версионируемый JSON, привязка к org. Идентификаторы возражений/сигналов/критериев в правилах — канонические ID общей таксономии (`taxonomy.json`, [doc 05](05-exchange-format.md) §6) — это делает скоры аналитики и тренажёра сравнимыми per-criterion без сцепки продуктов:

```json
{
  "rubric_id": "default_b2b_v1", "version": 3, "max_score": 100,
  "items": [
    {"id": "greeting", "title": "Приветствие: компания + имя", "weight": 5,
     "rule": {"kind": "lexicon", "lexicon": "script:greeting", "scope": "first_60s"}},
    {"id": "needs", "title": "Выявление потребностей ≥ 3 открытых вопросов", "weight": 15,
     "rule": {"kind": "predicate", "metric": "agent_open_questions", "op": ">=", "value": 3}},
    {"id": "objections", "title": "Возражения отработаны", "weight": 20,
     "rule": {"kind": "signal", "signal": "objection", "condition": "handled_success_ratio >= 0.5"}},
    {"id": "next_step", "title": "Зафиксирован следующий шаг", "weight": 15,
     "rule": {"kind": "signal", "signal": "next_step_agreed"}},
    {"id": "forbidden", "title": "Нет запрещённых фраз", "weight": 10,
     "rule": {"kind": "violation", "violation": "forbidden_phrase", "op": "==", "value": 0}}
  ]
}
```

### 4.2 Объяснимость (ключевое требование)

Каждый пункт рубрики → `score_items[]` с: полученным баллом, весом, **массивом evidence** (id находки → цитата + таймкод + роль + метод определения), и текстовым объяснением генерируемым шаблоном (не LLM — детерминизм и аудит). Итоговый скор = нормированная сумма; изменение рубрики помечает звонки для рескоринга (фоновая задача, версия рубрики в каждой записи).

### 4.3 Ручная проверка

РОП может изменить пункт оценки вручную (обоснование обязательно) — изменение пишется в `labels` и участвует в переобучении голов.

### 4.4 NLI-голова скоринга (переиспользование из SaaS-тренажёра)

Дополнение к rule-engine: пара «реплика клиента → ответ агента» прогоняется через NLI-голову multitask_v2 (Entailment = пункт рубрики выполнен, Contradiction = критическая ошибка/нарушение скрипта) — готовый генератор `violations` и evidence для `score_items` при латентности ~6.5 мс/пара. Аудит модели тренажёра, решение о переиспользовании (веса — нет, архитектура/пайплайн/чистый корпус — да) и план дообучения на InfoBayAI: [doc 07](07-nli-rubert-reuse.md), ADR-14.

## 5. Эмбеддинги и семантический поиск (`polylog.embeddings`)

| Вектор | Модель | Гранулярность | Назначение |
|---|---|---|---|
| фраза | USER2-base | utterance/sentence | поиск похожих фрагментов, кластеризация возражений |
| звонок | USER2-base, взвешенный пул фраз (вес = длительность × значимость реплик) | call | «похожие звонки», фича риск-модели |
| профиль компании/продукта | USER2-base по документам org (карточки, скрипты) | entity | сопоставление «что обсуждали ↔ какой продукт», обогащение контекста |
| паттерн возражения | центроиды кластеров возражений | pattern | трекинг новых вариантов возражений, эволюция таксономии |

Хранение: pgvector `halfvec(768)`, HNSW (m=16, ef_construction=64), метаданные в строке (org_id, entity_type, entity_id, ts) → фильтрация на уровне запроса. Оценка retrieval-качества на eval-наборе ≥ 50 пар (Recall@5 ≥ 0.85, MRR), бенчмарк 2 моделей минимум. Переиндексация при смене модели — фоновая, с версионированием `model_id` в векторах.

Pseudo-код запроса похожих звонков:

```sql
SELECT c.id, c.started_at, 1 - (e.vector <=> $1) AS sim
FROM embeddings e JOIN calls c ON c.id = e.entity_id
WHERE e.entity_type = 'call' AND e.model_id = $2 AND e.org_id = $3
  AND c.started_at BETWEEN $4 AND $5
ORDER BY e.vector <=> $1 LIMIT 20;
```

## 6. Предиктивная аналитика риска (`polylog.risk`)

> Полный реестр моделей предиктивного контура (M1–M10, каденсы, cold-start, витрины и UI-экраны, включая вкладку «Аналитика компании» по графу телефонов) — [doc 08](08-predictive-analytics.md). Ниже — базовая риск-модель сделки.

### 6.1 Задача (по контракту ML-практик)

- **Целевая переменная:** `deal_lost_within_days(14|30)` / вероятность выигрыша для активных сделок; альтернативная формулировка — «звонки после которых сделка была потеряна» (call-level суррогат).
- **Метрика успеха:** AUC-ROC ≥ 0.70 на time-based holdout + калибровка (Brier) + покрытие (доля решений при abstention). Базовая линия: логистическая регрессия на структурных метриках (talk_ratio, паузы, скор) — модель должна побить её на ≥ 0.05 AUC, иначе в проде остаётся база.

### 6.2 Фичи

| Группа | Примеры |
|---|---|
| Эмбеддинги | вектор звонка (PCА до 64 dim или как есть), сходство с векторами проигранных/выигранных звонков (kNN-признаки) |
| Структурные | talk_ratio, паузы, interruptions, вопросы, темп |
| События | возражения (типы, доля отработанных), сигналы, стадии, запрещённые фразы |
| Граф | число звонков в цепочке, дней с первого касания, доля неотвеченных, длина тишины в днях, активности в CRM |
| CRM | стадия сделки, сумма, источник (если разрешено org) |

### 6.3 Модель и объяснимость

- **CatBoost** (табличные фичи + эмбеддинги, категориальные — handle нативно), CPU-инференс.
- **SHAP (TreeExplainer)** — топ-3 фактора риска на звонок, показываются рядом с вероятностью; запрет показывать «голую» вероятность.
- **Калибровка**: isotonic/Platt на holdout; отчёт reliability curve.
- **Abstention**: до набора org ≥ 100 закрытых сделок — используется глобальная cold-start модель с пометкой «черновая оценка»; ниже порога уверенности — «недостаточно данных» вместо числа.
- **Дрейф**: PSI по фичам (еженедельно), деградация AUC на свежих метках (ежемесячно), алерты; правило retrain — при PSI > 0.2 или AUC < baseline+0.03.
- **Гигиена:** time-based split; запрет leakage (фичи только из данных на момент звонка); метки по сделкам с учётом delay; исключение удалённых ПДн из датасетов (см. [doc 04](04-security-152fz.md)).

## 7. Граф и Customer 360 (`polylog.graph`)

### 7.1 Сущности и рёбра

- Сущности: `phone_number`, `contact`, `company`, `lead/deal`, `call`, `interaction` (email/chat/meeting), `user(agent)`.
- Рёбра (`entity_links`): `has_phone`, `belongs_to`, `works_at`, `placed_call`, `mentions` (из NER транскрипта), `same_as` (слияние дублей).
- Каждое ребро: `source` (crm | phone_match | ner_match | manual), `confidence`, `evidence` (id находки).

### 7.2 Цепочка звонков

- `calls.previous_call_id` — линкedList по контакту; `calls.thread_id` = id корневого звонка (O(1) выборка всей цепочки). Пересчёт цепочки — при изменении связей (слияние контактов, перепривязка).
- Реконструкция: коннектор присылает звонки в произвольном порядке → сервис после вставки пересобирает chain для затронутого контакта (транзакционно).

### 7.3 Customer 360 API

`GET /api/v1/customers/{contact_id}/360` — одним ответом: таймлайн всех взаимодействий, цепочка звонков с скорами и трендом, топ-возражения по истории, риск сделки, граф-соседи (визуализация React Flow в UI), согласия и ретенции.

Контекст предыдущих звонков подмешивается в анализ текущего звонка (в промпт головы — не LLM, а фичи: «звонок #3 в цепочке, на прошлом не отработано возражение „цена“»).

Графовые запросы v1 — рекурсивные CTE (масштаб МСБ — тысячи контактов); Apache AGE — опциональное расширение, контракт API не меняется.

## 8. Дообучение на-prem (`polylog.training`, профиль `trainer`)

### 8.1 Источники лейблов

- Правки ролей в редакторе транскрипта → диаризация/ASR-фидбек.
- Правки возражений/сигналов/скоров РОПом → датасеты голов.
- Исходы сделок из CRM (win/loss) → риск-модель.
- Ручная разметка eval-набора (обязательные 50 звонков на онбординге).

### 8.2 Пайплайн

```
labels → dataset_builder (версия датасета, DVC-стиль: hash, состав, PII-чек)
→ training_run (LoRA на RuModernBERT для головы X | head-retrain | CatBoost refit)
→ eval_suite (см. §9) → model_registry (артефакт, метрики, чекпойнт)
→ canary (5% новых звонков) → promote/rollback
```

- Всё локально: LoRA r=16 на 8 ГБ VRAM, ночные окна по расписанию; инференс голов может переключаться на LoRA-мердж без даунтайма.
- Гигиена (обязательная): версия данных + гиперпараметры + seed в `training_runs`; eval до обучения; проверка PII в датасете; две версии моделей могут жить параллельно (A/B на стадии canary).

## 9. Качество ML: eval-харнесс (обязательный компонент)

| Харнесс | Что меряет | Порог/правило | Когда |
|---|---|---|---|
| ASR WER | по golden-набору (50 звонков per-org, эталонная разметка) | WER ≤ 15% телефонный домен; деградация > 3 п.п. = алерт | онбординг, каждый релиз моделей, еженедельно по выборке |
| Головы (возражения/сигналы) | F1 per class, precision на high-confidence | F1 ≥ 0.75 (v1); регрессия к прошлой версии — блокер релиза | каждый training_run + CI |
| Retrieval | Recall@5, MRR на eval-наборе | Recall@5 ≥ 0.85 | смена эмбеддера |
| Риск | AUC, Brier, coverage (abstention) | AUC ≥ 0.70, побитие baseline | каждый рефит |
| Дрейф | PSI фич, WER-тренд | PSI > 0.2 → retrain | еженедельно |
| Сквозной smoke | синтетический звонок (фикстура-аудио) проходит E2E | полный пайплайн < 10 мин | CI + healthcheck |

Golden-наборы хранятся в `eval_sets` с версиями; ручные правки пользователей пополняют наборы (с согласия org — настройка). Источники golden-наборов для M1 (бенчмарк ASR 8 кГц, диаризация, разметка возражений) — открытые датасеты, план работы с ними: [doc 06](06-datasets.md).
